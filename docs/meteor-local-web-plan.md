## 1. 결정과 목표

`~/WebstormProjects/codexm/`을 개발 프로젝트로 사용하고, Meteor.js와 React로 로컬 웹을 만든다. 기존 `codeasy-digix/codexm` 저장소의 이력과 Go 관리 서비스를 이어 사용한다. 웹, CLI, TUI, 플러그인에서 같은 작업·계정·설정을 조작하게 하며, 계정 전환 규칙을 웹에 다시 구현하지 않는다.

화면 배치와 조작은 사용자가 제시한 ChatGPT GUI 앱에 최대한 맞춘다. 스타일은 기본 HTML 요소와 단순한 일반 CSS로 구성하고, CSS의 주 용도는 레이아웃·간격·크기 조절로 제한한다. 계정 관리 기능도 이 채팅 중심 화면 안에서 자연스럽게 접근할 수 있게 한다.

현재 TUI와 플러그인은 화면 구현과 제공 범위가 다르지만, 작업 실행·계정 정책·사용 기록을 담당하는 Go supervisor를 공유한다. 새 웹의 핵심은 이 공통 기능에 완전한 조작 화면을 제공하고, 재접속과 여러 화면의 동시 사용을 견딜 공개 연결 계약을 추가하는 것이다.

웹에서 새 작업을 시작하고 기존 대화를 선택해 추가 지시를 보내며, 계정 등록·로그인·우선순위·한도·세션별 교체·로그·설정을 관리한다. 실제 모델 실행과 도구 사용은 공식 Codex 엔진이 수행한다. 목록 조회, 설정 변경, 정해진 계정 교체와 감시는 모델을 호출하지 않는다.

이 계획은 기존 저장소 지침의 플러그인 전용 GUI 방향을 사용자의 새 로컬 웹 요청에 맞춰 확장한다. 구현을 시작할 때 AGENTS.md와 제품 안내를 함께 갱신한다. 이번 단계의 산출물은 계획 문서이며 설치, 실행 중인 작업 인계, 계정 변경, 원격 적용은 후속 구현 범위다.

현재 호출 근거는 [TUI](../internal/tui/tui.go), [명령 목록](../internal/tui/commands.go), [플러그인 도구](../internal/plugin/mcp.go), [플러그인 화면](../plugin/ui/app.mjs), [관리 API](../internal/supervisor/api.go)다. 기존 플러그인 HTML을 그대로 옮기기보다는 화면을 React 컴포넌트로 구성하고, 기능과 검증 규칙은 공통 Go 코드에서 재사용한다.

기능 동등성의 기준은 플러그인 화면 전체와 CLI 전용 관리 기능을 합친 목록이다. 생성 폼의 고급 설정에는 CLI가 지원하는 모델·추론 강도·읽기 전용·완료 검사·그룹 등도 포함한다. 현재 API의 목표 예산 인자와 fork는 추가 개발이 필요하므로 화면 이식만으로 완료 처리하지 않는다.

Meteor 3 계열을 사용한다. 조사 시 공식 문서의 현재 버전은 3.5.2이므로 초기 후보로 삼고, 구현 착수 시 설치 가능한 안정 버전을 확인해 `.meteor/release`와 의존성 잠금 파일에 고정한다. Node 버전도 해당 Meteor 빌드의 요구사항에 맞춰 고정한다. [Meteor 변경 이력](https://docs.meteor.com/history)

### 3.1 연결 방식

새 명령 `codexm bridge --stdio`를 추가하는 방향을 채택한다. 이는 아직 존재하지 않는 계획 명령이다. Meteor가 검증된 절대 경로의 codexm을 셸 없이 한 번 실행하고, 요청·응답·변경 알림을 같은 연결에서 주고받는다. 웹 요청마다 CLI를 실행하거나 사람이 읽는 출력·TUI 화면을 분석하지 않는다.

기존 Unix 소켓 `/rpc`를 Node에서 바로 호출하는 방법은 초기 조회에는 가능하지만, 최초 관리자 선택 전의 로그인과 설정, 버전 검사, 오류 분류를 Node에 중복 구현하게 된다. 현재 supervisor는 관리자 계정이 있어야 시작되며, 플러그인의 LoginBroker와 최초 설정은 supervisor 외부에 있다. 이 기능을 Go의 공통 응용 계층으로 추출하고 CLI·플러그인·브리지가 같이 사용한다.

브리지가 종료되어도 supervisor와 작업 엔진은 계속 살아 있다. Meteor 재시작은 브리지 재연결과 구독 복구만 수행한다. 브리지 재시작으로 중단된 로그인 절차는 실패·만료 상태를 표시하고 다시 시작할 수 있게 한다. 열린 웹 탭 수만큼 브리지나 supervisor를 만들지 않는다.

개발 hot reload와 비정상 종료에서도 브리지 중복 실행을 막고 자식 프로세스를 정리한다. 로그인 절차는 인증된 브라우저 세션별 소유자를 가지며, 로그인 ID만 안다고 다른 세션이 코드를 읽거나 취소할 수 없게 한다. 같은 브라우저의 재연결은 소유자를 유지한다.

### 3.2 Meteor 데이터 사용

Meteor의 사용자 정의 publication으로 Go에서 받은 자료와 변경분을 클라이언트에 전달한다. 이 API는 `added`, `changed`, `removed`로 자료를 직접 게시할 수 있다. [Meteor publication API](https://docs.meteor.com/api/meteor.html#Meteor-publish)

작업·대화·계정·이벤트를 MongoDB에 다시 저장하지 않는다. 서버 측 Mongo 의존성을 제거한 최소 구성으로 개발·배포 빌드가 가능한지는 초기 기술 검증에서 확인한다. 패키지 때문에 Mongo가 필요하다면 의존성을 정리하는 것을 우선하며, 핵심 데이터를 복제하는 해결책은 사용하지 않는다. 브라우저에는 필요한 화면 자료만 임시 보관한다.

## 4. 프로젝트와 설치 경로

개발 저장소는 기존 `codeasy-digix/codexm`의 같은 Git 이력을 사용한다. 구현 단계에서 요청 경로에 체크아웃을 준비하고, 기존 작업 디렉터리의 진행 중 작업과 충돌하지 않도록 전환한다. 독립 저장소 두 곳에 Go 코드를 복제하지 않는다.

~~~text
~/WebstormProjects/codexm/
  cmd/                       기존 codexm 실행 진입점
  internal/                  기존 계정·실행·저장·서비스 코드
    application/             공통 관리 기능 추출 예정
    bridge/                  버전 있는 JSON 연결 예정
  plugin/                    기존 플러그인과 호환 진입점
  web/                       Meteor 프로젝트
    .meteor/
    client/
    server/                  인증·브리지·methods·publications
    imports/ui/              작업·계정·기록·설정 화면
    imports/ui/styles/       작은 base.css와 layout.css
    imports/contracts/       공통 계약에서 생성한 타입
    tests/
  contracts/                 브리지 스키마와 호환성 자료
  docs/                      계획·사용법·검증 결과
~~~

루트는 제품 전체의 프로젝트이고 `web/`이 Meteor 앱이다. Go와 웹은 같은 릴리스에서 호환성을 검사하되, 기존 CLI만 설치해서 쓰는 경로도 유지한다.

| 경로 | 용도 |
| --- | --- |
| `~/.config/codexm/config.toml` | 기존 정책·관리자·로그 설정, 추가 웹 설정 |
| `~/.local/state/codexm/` | 기존 관리 DB·작업 기록·복구 큐, 웹 실행 상태·로그 |
| `~/.local/share/codexm/` | 설치된 바이너리·보관 엔진·플러그인·버전별 웹 빌드 |
| `~/.codex/`, 기존 계정 저장소 | 공식 대화와 인증 자료, 기존 위치 유지 |
| `~/.home/tools/codexm/` | 같은 제품의 고정 revision 복구·빌드·설치 호출 |
| `~/.home/manifests/home.json` | 웹의 의존성·검증·실행 명세 확장 |
| `~/.home/private/<profile>/` | 기존 알림 비밀 설정, 웹으로 복사하지 않음 |

`.home`에는 제품 소스를 복사하지 않는다. 기존 `config/home/codexm-revision.txt`와 설치 호출 구조를 확장한다. 로컬 검증 후에만 설치 핀을 갱신하며, `remote-mac` 적용은 별도 후속 단계로 둔다.

## 5. 데이터와 실행 소유권

| 정보 | 원본과 쓰기 책임 |
| --- | --- |
| 공식 대화 목록 | 공식 SQLite를 Go catalog가 읽기 전용 조회 |
| 대화 본문·도구 결과·목표 | 공식 엔진과 공식 대화 저장소 |
| 관리 작업·실행 회차·계정 변경·복구 | codexm 관리 SQLite, supervisor가 기록 |
| 계정 인증 | 기존 계정 저장소와 공식 로그인 절차 |
| 정책과 설정 | 기존 config.toml, 공통 설정 저장 함수 |
| 브라우저 초안·화면 배치 | 로컬 브라우저 저장소, 호스트와 대화별 분리 |

공식 대화의 원본은 공식 저장소에 두고, codexm DB에는 관리에 필요한 상태·요약·사건을 저장한다. 현재 저장되는 마지막 입력과 목표 snapshot 등도 복구에 필요한 범위에서 유지한다. 공식 SQLite에 `codexm_*` 테이블을 추가하지 않으며 Node가 직접 열지도 않는다. 현재처럼 WAL을 포함한 읽기 전용 조회와 스키마 검사를 유지한다. 공식 대화 목록 오류가 관리 DB를 초기화하거나 대화를 삭제하는 원인이 되어서는 안 된다.

대화의 기본 식별자는 `(호스트, 대화 저장소, thread_id)`다. Job과 Run ID는 별도로 유지한다. fork와 엔진 버전에 따라 세션 메타데이터가 달라질 수 있으므로 `session_id`와 `thread_id`가 같다고 전제하지 않는다. 부모 관리 작업과 공식 엔진이 만든 하위 에이전트도 구분한다.

일반 채팅은 한 턴이 끝나면 추가 입력을 기다린다. 목표가 없는 작업에 자동으로 goal을 만들거나 계속하라는 메시지를 반복해서 보내지 않는다. 사용자가 일시 중지한 작업, 완료 목표, 목표 예산 제한은 계정 교체 때문에 다시 활성화하지 않는다.

## 6. 연결 계약과 상태 누락 방지

### 6.1 공개 계약

브리지는 `protocolVersion`, 제품 버전, 연결된 supervisor 버전, 엔진 기능 목록을 초기 응답으로 보낸다. 기능 지원 여부에 따라 화면 조작을 활성화한다. 원시 내부 RPC나 임의 명령 문자열을 브라우저에 노출하지 않는다.

계약은 다음 기능군으로 나눈다. 이름은 구현 시 확정하되 책임과 결과 형식은 함께 검증한다.

| 기능군 | 포함할 동작 |
| --- | --- |
| 연결과 초기 설정 | capabilities, 상태, 최초 계정 목록, 관리자 설정, 서비스 시작 |
| 대화와 작업 | 목록·검색·본문 페이지·상세·등록·해제·생성·재개·전송·중지 |
| 계정 | 로그인 시작·상태·취소, 한도, 우선순위, 기본 로그인, 세션 전환 |
| 실행 제어 | 승인·질문 답변, 목표, 전환·복구 진행 조회, 미확정 동작 해결 |
| 기록과 설정 | 전체·작업·계정 기록, 설정 읽기·검증·저장, 알림 설정 |
| 명시적 관리자 | 범위를 선택한 관리자 호출과 호출 기록 |

오류는 문자열뿐 아니라 `code`, 사용자가 이해할 설명, 재시도 가능 여부, 관련 작업 ID를 제공한다. 예시는 인증 필요, 외부 실행 중, 설정 충돌, 미지원 엔진, 연결 끊김이다. 인증 토큰이나 전체 내부 설정은 결과에 포함하지 않는다.

### 6.2 재연결과 사건 전달

현재 `events` API는 최근 100건 조회이며 모든 설정·계정 변경을 대표하는 연속 구독 API가 아니다. 이 경로를 그대로 실시간 웹에 사용하면 오래 끊겼을 때 상태를 놓칠 수 있다.

관리 DB에 변경 번호가 있는 journal을 추가하거나 기존 사건 구조를 확장한다. 관리 DB 안의 작업·실행·계정 관측·승인 변경은 상태 갱신과 같은 트랜잭션에 기록한다. config.toml과 인증 파일은 DB와 별개이므로 공통 Go 저장 함수의 잠금·revision 검사를 유지하고, 저장 후 관측한 revision을 journal에 기록한다. 저장과 기록 사이에 종료되어도 재시작 시 파일 revision을 대조해 복구한다. 외부 공식 대화 목록 변화는 별도의 catalog revision과 재조회로 반영한다.

1. 접속 시 관리 DB snapshot과 그 시점의 `sequence`를 일관된 읽기로 함께 받는다. 설정과 공식 대화 목록은 각각 revision·관측 시각을 붙이며 다른 저장소까지 하나의 원자적 snapshot이라고 가정하지 않는다.
2. 그 이후 변경을 순서대로 구독한다. 중복 사건은 번호로 제거한다.
3. 재연결 시 마지막 번호부터 이어 받는다. DB 교체 여부를 알 수 있게 저장소 식별자도 포함한다.
4. 보관 기간 만료나 번호 누락이면 전체 snapshot을 다시 받고, 사용자의 선택·입력 초안·스크롤은 유지한다.
5. 브리지와 supervisor의 주기적 상태 대조로 연결 중 발생한 누락도 복구한다.

텍스트 스트림은 짧게 묶어서 전송하고 최종 내용은 공식 대화 이력으로 대조한다. 출력 조각마다 관리 DB에 별도 대화 복사본을 만들지 않는다. 승인·오류·계정 교체·턴 종료는 출력량과 무관하게 전달한다. 느린 클라이언트의 큐는 제한하고, 넘치면 재동기화를 지시한다.

공식 SQLite 파일 변경 감지는 재조회 신호로만 사용한다. WAL 파일 감시만으로 모든 변경을 보장하지 않으며, 검색 페이지의 제한된 재검증을 병행한다. 전체 대화를 수초마다 다시 보내는 방식은 제거한다.

### 6.3 중복 실행 방지

Meteor 메서드는 연결 복구 때 재호출될 수 있다. 따라서 새 작업, 메시지 전송, 승인 응답, 계정 변경처럼 부작용이 있는 요청에는 클라이언트가 만든 `operation_id`를 붙인다. [Meteor 메서드 재시도 설명](https://docs.meteor.com/api/meteor.html#Meteor-methods)

supervisor는 요청 ID·요청 내용의 해시·진행 상태·결과를 저장한다. 동일 요청은 같은 결과를 반환하고, 같은 ID에 다른 내용이 오면 거부한다. 중간에 프로세스가 끊긴 요청은 공식 실행 상태를 대조한다. 결과가 불명확하면 메시지나 fork를 무조건 재실행하지 않고 확인이 필요한 상태로 남긴다.

supervisor가 아직 없는 최초 설정은 공통 설정 함수의 잠금과 revision으로 중복 저장을 막는다. 로그인 시작·취소는 브라우저 소유자와 요청 ID로 중복을 제어하며, 브리지 재시작 뒤 로그인 시작을 자동 재전송하지 않는다. 저장된 계정 상태를 확인한 뒤 화면에서 다시 진행한다.

설정 편집은 기존 revision 검사를 재사용한다. 계정 전환은 예상 Run ID, 승인 응답은 요청 ID와 Run ID를 함께 검사한다. 다른 탭에서 먼저 완료한 조작을 오래된 화면이 덮어쓰지 않게 한다.

## 7. 계정 관리 화면

계정 관리는 첫 화면의 주요 메뉴로 둔다. 아래 네 가지를 서로 다른 항목으로 표시한다.

| 항목 | 의미와 적용 범위 |
| --- | --- |
| 작업 계정 우선순위 | 새 자동 작업과 한도 복구에서 사용할 순서 |
| 현재 작업의 계정 | 선택한 작업의 이번 실행과 전환 요청 |
| 관리자 계정 | 사용자가 명시적으로 요청한 관리자 모델 호출 |
| Codex 기본 로그인 | 공식 CLI·GUI의 공용 기본 인증 |

작업용 별도 default 계정은 다시 도입하지 않는다. 기본 정책은 `account-work → account-secondary → account-main`, 세 계정의 한도 소진이 확인되면 `account-backup`을 사용하는 기존 정책이다. 조회 실패·미확인은 소진과 구분한다. 예비 계정 사용 중에는 600초 간격으로 우선 계정의 회복을 확인하고, 가능한 계정으로 기존 안전한 전환 절차를 수행한다.

계정 행에는 닉네임, 로그인 상태, 현재 실행 작업 수, 단기·장기 잔여량, 갱신 시각, 재설정 시각, 마지막 조회 오류를 표시한다. 한도 창이 여러 종류이면 이름과 기간을 함께 표시하며 무조건 5시간으로 가정하지 않는다.

로그인은 계정 추가 또는 재로그인에서 시작한다. 브라우저 인증과 기기 코드 방식, 진행 상태, 취소, 완료 후 새로 고침을 제공한다. 현재 기본 로그인을 바꾸는 조작에는 적용 범위를 함께 표시한다. 작업 우선순위 저장이나 세션 계정 변경이 공용 로그인까지 바꾸지 않게 한다.

공용 기본 로그인 변경은 이후 공식 실행이 사용할 인증을 바꾸는 기능이다. 이미 실행 중인 GUI 대화의 계정까지 즉시 바뀐다고 표시하지 않는다.

수동 계정 변경은 요청됨 → 현재 실행 정리 → 소유권 해제 확인 → 새 계정 연결 → 재개 결과의 상태를 보여준다. 운영 중 타임아웃이 나면 실제 실행 상태를 확인할 수 있고, 이미 처리된 변경을 중복 요청하지 않는다. 계정 인증 실패와 한도 소진은 서로 다른 해결 동작을 제시한다.

## 8. 작업 화면과 직접 명령

### 8.1 ChatGPT 앱과 같은 화면 구성

기본 화면은 왼쪽 사이드바, 중앙 대화, 하단 입력창으로 구성한다. 계정·실행·목표 상세는 필요할 때 오른쪽 패널로 열며 기본 채팅 공간을 먼저 확보한다. 전체 계정 카드와 관리 지표를 기본 대화 화면에 항상 펼쳐 두지 않는다.

| 위치 | 화면과 조작 |
| --- | --- |
| 왼쪽 사이드바 | 새 채팅, 검색, 프로젝트와 대화 목록, 즐겨찾기, 접기·펼치기 |
| 대화 상단 | 제목·프로젝트, 모델과 현재 작업 계정, 실행 상태, 상세 열기 |
| 중앙 대화 | 읽기 편한 본문 너비, 사용자·에이전트 메시지, 코드·도구 결과, 이전 기록 |
| 하단 입력창 | 내용에 따라 높이가 늘어나는 입력, 전송·중지, 지원되는 첨부, 기본 포커스 |
| 필요할 때 여는 패널 | 선택 작업의 계정 변경, 실행 회차, 목표, 승인·복구 상세 |
| 관리 진입점 | 사이드바의 계정·사용 기록·설정, 동일 기능의 직접 명령 |
| 설정 화면 | 앱 설정처럼 왼쪽 항목 목록과 오른쪽 편집 내용, 저장 상태·입력 오류 표시 |

화면 전환 뒤에는 선택 대화와 초안을 유지한다. 새 채팅, 대화 선택, 검색, 전송·중지, 설정 열기의 위치와 동작을 ChatGPT 앱과 가깝게 맞춘다. 제품 이름과 계정 실행 정보는 codexm의 실제 상태를 표시한다. 구현 검토에서는 사용자가 제공한 앱 화면과 나란히 비교해 주요 배치와 조작의 일관성을 확인한다.

### 8.2 단순한 CSS 원칙

시맨틱 HTML과 브라우저 기본 button, input, textarea, select, checkbox, dialog를 우선 사용한다. 별도 UI 프레임워크, Tailwind·Bootstrap·MUI 같은 스타일 패키지, CSS-in-JS는 도입하지 않는다. 기본 타이포그래피와 최소 가독성 규칙은 `base.css`, Grid·Flex 배치와 간격·크기는 `layout.css`에 둔다.

CSS는 사이드바와 본문 배치, 입력창 위치, 스크롤 영역, 패널 너비와 좁은 창에서의 접힘을 중심으로 작성한다. 시스템 글꼴과 소수의 색상·간격 변수만 사용하며, 배경·글자색·테두리·키보드 포커스는 읽기와 조작에 필요한 정도로 적용한다. 앱과의 유사성은 구조와 동작을 기준으로 맞추고 그림자·그라데이션·장식 애니메이션·세밀한 픽셀 재현은 요구하지 않는다.

레이아웃은 고정 좌표 대신 Grid·Flex로 구성한다. 작은 창에서는 사이드바와 상세를 접는 정도로 대응한다. 반응형 규칙이나 컴포넌트별 스타일이 불필요하게 늘어나면 구조를 단순화한다. 기능 추가 시 기존 기본 요소와 레이아웃 규칙을 재사용한다.

### 8.3 목록과 대화 기능

전체 대화 검색은 관리 등록 여부와 무관하게 동작한다. 보관 대화, 프로젝트 폴더, 상태, 계정, 관리 중 필터와 기존 플러그인의 별표·즐겨찾기 필터를 제공한다. 즐겨찾기 등 화면 선호 정보는 호스트·대화별 브라우저 저장소에 두며, 플러그인 origin의 저장값이 독립 웹으로 자동 공유된다고 가정하지 않는다. 목록 선택 자체는 작업 실행이나 계정 변경을 발생시키지 않는다. 새 작업은 폴더·계정 정책·실행 설정을 지정하고 일반 대화 또는 명시적인 목표 작업으로 만든다.

본문은 최신 턴부터 필요한 만큼 불러오며 이전 기록을 더 볼 수 있다. Markdown, 코드, 도구 실행 상태, 결과, 승인·질문을 표시한다. 파일·이미지 입력과 첨부 표시 등 현재 관리 API에 없는 기능은 공식 엔진 capability를 먼저 확인해 공통 계층에 추가한다. 미지원 기능을 일반 문자열로 보내서 성공한 것처럼 처리하지 않는다.

입력창은 기본 포커스를 유지한다. Enter 전송, Shift+Enter 줄바꿈, 한국어 입력 조합 중 Enter 보호, 대화별 초안, 이전 입력 기록을 지원한다. 위아래 키는 입력창의 커서·기록에 사용하며 목록 이동에 가로채지 않는다. 목록은 클릭 또는 별도 단축키로 이동한다. 새 대화에 불필요한 줄바꿈이나 자동 전송을 넣지 않는다.

명령 팔레트는 `/` 또는 단축키로 연다. `/manage`, `/accounts`, `/usage`, `/logs`, `/settings`, `/status`는 웹에서 직접 화면이나 기능을 실행하며 모델로 보내지 않는다. `/manager`와 일반 대화 입력만 표시된 범위의 모델 요청을 발생시킨다. 명령 이름, 도움말, 버튼은 하나의 명령 정의를 공유한다. 지원하지 않는 공식 Codex 명령은 설명과 공식 TUI 열기 경로를 제공한다.

공식 TUI 열기는 로컬의 새 터미널에 연결하는 기존 기능을 재사용한다. 브라우저 안에 셸 터미널을 만드는 기능은 별도 범위이며 첫 버전의 필수 항목으로 넣지 않는다. 웹의 작업 열람 연결도 기존 viewer 수명과 맞춰 heartbeat·종료를 처리해 완료한 작업 엔진이 불필요하게 남지 않도록 한다.

진행 중 추가 지시는 다음 입력으로 대기시키는 동작과 현재 턴에 전달하는 동작을 명확히 나눈다. 승인·질문은 정확한 요청에 답변하며, 계정 변경으로 사라진 승인 요청은 만료 표시한다. 새 사건 도착 때문에 목록이 계속 늘어나거나 읽고 있는 위치가 자동으로 아래로 이동하지 않게 한다.

설정 화면은 관리자·계정 정책, 동시 실행 수, 재확인·사용량 수집 간격, 알림, 웹 연결 설정으로 구성한다. 서비스 진단에는 supervisor·watchdog·웹의 상태, 제품·엔진 버전, 최근 실패를 표시한다. 시작·중지·업그레이드와 엔진 갱신은 기존 서비스 기능을 사용하고 적용 범위와 실행 중 작업에 미치는 영향을 화면에서 안내한다.

## 9. 기존 GUI 대화와 목표 인계

새 웹에서 생성한 작업은 처음부터 codexm이 공식 엔진의 실행을 소유한다. 따라서 한도 감지와 계정 전환을 같은 관리 경로에서 수행할 수 있다.

기존 공식 GUI가 실행 소유권을 가진 대화는 등록·열람할 수 있지만 웹으로 옮겼다는 이유로 소유권이 해제되지는 않는다. 현재 확인된 API 경계에서는 GUI의 중지 버튼만으로 같은 대화의 계정 교체가 보장되지 않는다. 외부 실행 중 상태를 표시하고, 실제 소유권 해제가 확인된 뒤 같은 대화를 재개한다.

분기가 필요한 경우 사용자가 선택한 시점의 이력을 기반으로 새 대화를 만드는 별도 동작을 제공할 수 있다. 이는 신규 개발 항목이다. 원본·분기 대화의 연결을 기록하고 같은 폴더의 동시 쓰기 충돌을 검사한다. Git 작업은 분리된 worktree를 권장하되 미커밋 변경이 자동 복사된다고 가정하지 않는다.

goal이 있는 대화의 분기는 목표 본문뿐 아니라 상태·누적 사용량·남은 예산의 승계 여부를 먼저 검증한다. `deferGoalContinuation` 지원이 있더라도 예산 승계까지 검증되기 전에는 자동 진행을 제공하지 않는다. 예산 제한이나 사용자의 중지 의사를 분기로 우회하지 않는다.

기존 플러그인의 현재 대화 등록 훅은 호환 경로로 유지한다. 독립 웹에서는 선택한 대화를 명시적으로 등록하므로 GUI 입력창의 멘션 해석에 의존하지 않는다. 공식 GUI의 계정을 투명하게 바꾸는 기능을 이 웹 계획의 완료 조건으로 삼지는 않는다.

## 10. 사용 기록과 알림

사용 기록 화면은 전체를 기본으로 하고 작업·계정·기간·변경 사유로 좁혀 볼 수 있게 한다. 선택한 작업 안에서는 같은 기록 화면의 필터를 적용한다.

각 실행 회차에 작업 제목, 계정, 시작·종료 시각, 경과 시간, 한도 관측값, 계정 변경 시각과 사유를 표시한다. 경과 시간에는 실행 환경의 대기 시간이 포함된다는 점을 설명한다. 계정 한도 %는 계정 전체의 값이며 특정 대화만의 사용률로 표시하지 않는다. 세션 토큰은 공식 측정값이 있을 때만 보여 주며 미확인은 0으로 바꾸지 않는다.

한도 창이 초기화되거나 종류가 바뀌면 이전 구간과 차이를 계산하지 않는다. 모든 값에 관측 시각을 붙이고 로컬 시간대와 날짜를 표시한다. 등록 전의 과거 계정 사용 이력은 근거가 있을 때만 표시한다.

Discord는 기존 Go 알림 기능과 `.home`의 비밀 설정을 재사용한다. 기존 요청에 맞춰 5시간 한도 소진 알림에는 전체 등록 계정의 상태와 현재 작업 상태를 포함한다. 중복 방지는 서버에서 유지하고, 웹은 활성 여부·최근 결과·전송 실패를 보여준다. 단순 화면 열기나 새로 고침은 알림을 보내지 않는다.

## 11. 로컬 접속과 수명 관리

새 진입 명령은 `codexm web`으로 계획한다. 실행 중이면 기존 웹에 연결하고, 없으면 로컬 웹을 시작해 브라우저를 연다. `codexm web status`, `stop`, `logs`를 함께 제공한다. 기존 `codexm` TUI와 공식 `codex` 명령은 각각 독립적으로 사용한다.

첫 구현의 웹 실행은 사용자가 제어할 수 있는 이름 있는 tmux 세션을 사용한다. 개발은 `codexm-web-dev`, 로컬 설치본은 `codexm-web`으로 구분하고 실행 후 실제 세션 이름과 `tmux attach -t <이름>`을 안내한다. `web stop`은 그 웹과 브리지만 정리한다. 임시 검증 세션은 검증 종료 후 정리한다.

기존 supervisor·watchdog의 launchd/systemd 관리는 유지한다. 웹을 추가하면서 기존 작업을 tmux로 옮기거나 이중 supervisor를 만들지 않는다. 웹의 자동 시작 서비스가 필요해지는 후속 단계에서는 tmux와 OS 서비스 중 하나를 수명 관리 주체로 정하고 중복 실행을 방지한다.

프로덕션은 Meteor 개발 서버 대신 빌드된 Node 번들을 실행한다. 포트는 loopback 주소에만 바인딩하고 충돌 시 실제 주소를 출력한다. Meteor 개발 실행도 명시적으로 loopback에 바인딩한다. [Meteor 실행 옵션](https://docs.meteor.com/cli/#meteor-run)

브라우저 접속은 로컬 실행기가 발급한 일회성 접근 수단을 짧은 브라우저 세션으로 교환한다. 자격 증명을 URL query, 로그, 분석 도구나 브라우저 영구 저장소에 남기지 않는다. HTTP와 WebSocket 양쪽에 세션 인증·Origin/Host 검사를 적용하고 DDP의 재연결도 인증을 다시 확인한다. 인증 전에는 대화·계정 자료를 구독할 수 없다.

Cookie만으로 DDP가 인증된다고 전제하지 않는다. 인증된 같은 origin의 HTTP 요청으로 짧은 유효기간의 DDP 접속 ticket을 받고, 클라이언트 메모리에서 첫 인증 메서드에 전달해 서버가 연결에 권한을 부여하는 방식으로 설계한다. 재연결·세션 복원·hot reload에서도 권한 만료와 재인증을 확인한다. Meteor의 기본 연결 정보에는 Cookie가 제외되므로 이 경로는 초기 기술 검증에서 확인한다. [Meteor 연결 API](https://docs.meteor.com/api/meteor.html#Meteor-onConnection)

로그인 세션과 Codex 계정 토큰은 별개이며, Codex 토큰은 Go 측 저장소에 둔다. 도구 출력과 대화의 Markdown은 안전하게 렌더링하고 임의 HTML 실행을 허용하지 않는다. 파일 접근은 선택한 작업과 권한 정책에 맞는 API로 제한한다.

## 12. 업데이트와 기존 기능 보존

공식 Codex CLI 업데이트, codexm Go 업데이트, 웹 업데이트의 버전 경계를 구분한다. 설치된 엔진의 기능을 확인해 연결하고, 이미 실행 중인 작업의 엔진은 즉시 교체하지 않는다. 검증한 엔진 보관과 기존 runtime 갱신 절차를 이어 사용한다.

웹과 브리지의 계약이 맞지 않으면 읽을 수 있는 상태와 업그레이드 안내를 제공하고 새 쓰기 요청을 막는다. 호환성 문제 때문에 실행 중인 작업을 종료하지 않는다. 웹의 기존 연결이 끊어져도 새 버전에서 미완료 요청 결과를 확인할 수 있어야 한다.

플러그인은 초기 구현 동안 그대로 제공한다. 공통 응용 계층으로 필요한 로직을 추출하되 플러그인 동작을 함께 회귀 검사한다. 웹 전환 후에는 관리 기능을 공통 계층에 먼저 추가하고 각 화면이 그 계약을 사용하게 한다. 호스트 내부 패널 API나 앱 번들을 새 웹의 필수 의존성으로 만들지 않는다.

관리 DB 변경은 버전 있는 마이그레이션과 SQLite의 일관된 백업 절차를 사용한다. WAL 파일을 무시한 단순 복사를 백업으로 취급하지 않는다. 이전 바이너리가 새 DB를 읽을 수 없는 경우에는 버전 전환을 차단하고 복구 경로를 안내한다. 백업 복원은 새로 발생한 실행 기록을 잃을 수 있으므로 자동으로 덮어쓰지 않는다.

## 14. 검증 계획

첫 검증은 임시 상태 디렉터리와 가짜 엔진을 사용한다. 실제 계정의 한도를 일부러 소진하거나 진행 중인 작업을 종료해 시험하지 않는다. 이후 명시적으로 구분한 검증 작업으로 공식 엔진과 브라우저 동작을 확인한다.

| 검증 상황 | 통과 기준 |
| --- | --- |
| 웹 새로 고침·닫기·서버 종료 | 작업 계속 실행, 다시 열면 상태와 미완료 요청 복원 |
| 두 탭의 동일 전송·계정 변경 | 한 번만 실행, 같은 작업 결과 표시 |
| 응답 직전 브리지 또는 supervisor 종료 | 저장된 요청과 엔진 상태 대조, 불명확한 전송을 자동 반복하지 않음 |
| 장시간 연결 끊김·journal 만료 | 누락 감지 후 snapshot 복원, 입력 초안과 선택 보존 |
| 계정 한도 소진·조회 실패·회복 | 정책 순서 준수, 미확인을 소진으로 오판하지 않음, 예비 계정 재확인 |
| 목표 예산 소진·일시 중지·완료 | 다른 계정이나 fork로 자동 재개하지 않음 |
| 외부 GUI writer | 등록·열람 가능, 실행 소유권 없이 새 writer 생성하지 않음 |
| 설정 동시 저장·로그인 취소 | revision 충돌 안내, 인증 비밀 유출 없음, 다른 로그인 영향 없음 |
| 다른 브라우저의 로그인 조회·취소 | 로그인 소유자 검사로 거절, 정상 재연결은 진행 상태 유지 |
| 악의적 웹 origin·미인증 DDP | 작업·계정 접근과 쓰기 차단 |
| 공식 CLI 또는 웹 버전 변경 | capability에 맞는 동작, 기존 작업과 공식 `codex` 실행 보존 |

Go 실행 코드 변경에는 저장소 지침의 race 테스트와 vet, 관련 격리 통합 검사를 수행한다. 웹에는 계약 검사, 핵심 사용자 흐름의 브라우저 검사, 키보드·한국어 입력·스크롤 검사를 수행한다. 테스트 결과만으로 실제 GUI가 검증됐다고 쓰지 않고 확인한 화면과 흐름을 기록한다.

성능 목표는 개발 장비에서 측정할 수치로 잡는다. 예열된 상태에서 대화 1,000개 중 첫 페이지와 선택한 대화의 최근 기록을 각각 1초 이내 표시하고, 관리 사건의 화면 반영은 정상 로컬 연결에서 1초 이내를 목표로 한다. 초기 컴파일·로그인·모델 응답 시간은 별도로 측정한다. 목록 수가 늘어도 한 번에 내려받는 자료와 화면 행 수를 제한한다.

## 15. 최종 인수 기준

1. `codexm web`만으로 로컬 관리 화면을 열고 최초 로그인·관리자 선택까지 진행할 수 있다.
2. 기존 모든 대화를 볼 수 있고, 관리 등록·새 작업·추가 지시·계정 변경을 화면에서 직접 수행한다.
3. 계정 정책·설정·상태·로그가 CLI와 일치하며 별도 정책 DB나 Mongo 복사본이 없다.
4. 웹이 꺼져 있는 동안에도 supervisor가 감시하며, 다시 열면 변경과 실패 원인을 확인할 수 있다.
5. 재접속과 중복 클릭으로 작업·메시지·승인이 두 번 처리되지 않는다.
6. 계정 한도와 목표 예산을 구분하고 기존 GUI 실행 소유권을 존중한다.
7. 일반 관리 조작의 모델 호출은 0회이고 실제 작업·명시적 관리자 요청만 모델을 사용한다.
8. 기존 CLI·TUI·플러그인 기능과 공식 `codex` 실행에 회귀가 없다.
9. 설치·업데이트·실패 복구·tmux 제어 방법이 문서와 화면에서 일치한다.
10. ChatGPT 앱과 익숙한 채팅 배치·조작을 제공하고, 기본 HTML과 배치 중심의 작은 일반 CSS로 구성한다.

이 기준까지를 로컬 웹의 첫 완성 범위로 삼는다. 공식 Codex GUI 전체 복제, 원격 공용 서비스, 여러 사용자 협업, 앱 번들 패치는 포함하지 않는다. 기존 GUI의 모든 대화를 계정 교체까지 투명하게 제어하는 요구는 실행 소유권 API가 지원되는 범위에서만 확장한다.
