# codexm 작업 관리자

`codexm`은 여러 Codex 작업의 목록·로그·사용량·계정 전환을 관리하는 프로그램이다.
작업을 선택하면 새 터미널에서 해당 계정의 공식 Codex 세션을 연다. `/goal`은 선택 기능이다. 일반 채팅, 단발 작업,
지속 목표와 이들 사이의 관계를 같은 관리 화면에서 다룬다.

상주 프로그램은 Go로 만들고 사건 수집, 상태 저장, 한도 조회와 정해진 복구를
수행한다. 관리 에이전트는 사용자가 자연어로 관리 지시를 내리거나 규칙으로
해결하지 못하는 사건이 있을 때만 실행한다. 화면을 열거나 목록을 새로 고치거나
계정 사용량을 조회하는 동작은 모델을 호출하지 않는다.

`codexm 0.2.0` 소스는 독립 `codeasy-digix/codexm` 저장소에서 관리한다. 0.1.x 검증 기록은 이전 구현의 기록이다. 현재 독립 소스 빌드와 로컬 배포 준비만 제공한다. 실제 검사와 확인 범위는
[검증 기록](codexm-validation.md)에 보관한다.

```sh
codexm                 # 처음에는 관리자 계정 선택, 이후에는 작업 목록
codexm setup --manager account-backup  # 첫 선택을 CLI로 명시하는 방법
codexm new --cwd ~/projects/example --account account-work --prompt '작업 지시'
codexm resume THREAD_ID --account account-secondary  # 열람 대상으로 가져오기
codexm resume-job JOB_ID              # 소유권을 확인한 뒤 재개
codexm manage JOB_ID                  # 생성 없이 기존 대화를 관리 목록에 보관
codexm open JOB_ID                    # 새 터미널에서 공식 Codex 연결
codexm attach JOB_ID                  # 현재 터미널에서 연결 (SSH 등)
codexm logs                           # 전체 작업의 계정·실행시간·한도 사용률
codexm logs JOB_ID --json              # 선택한 작업의 저장된 기록
```

## Codex 하네스 활용 방식

권장 구성은 **공식 Codex 실행 엔진과 채팅 TUI를 활용하는 별도 관리 프로그램**이다.
도구 실행, 파일 편집, 대화 이력, 모델 통신, 권한 처리와 `/goal` 실행은 Codex에 맡기고,
작업 목록, 관리 지시, 계정 정책과 복구 상태는 `codexm`이 담당한다.

Codix의 진입점은 home 명세의 `tools/codix/codix`를 통해 별도 패키지를 실행한다.
이 패키지는 설정을 준비한 뒤 공식 Codex 바이너리를
`exec`한다. Codex 소스를 포크하거나 TUI를 재빌드하는 방식이 아니다.
같은 실행 엔진을 활용한다는 원리는 가져오되, Codix의 LM Studio 설정이나
특정 설치본의 환경 격리 구현을 그대로 복사하지 않는다.

| 구성 방법 | 판단 |
| --- | --- |
| 셸 래퍼로 계정 전환과 `codex resume`만 연결 | 기존 채팅 UI 활용에는 유용하지만 통합 목록과 사건 저장에는 부족하다. |
| Go 관리 TUI와 공식 app-server 연결 | 기본 선택이다. 관리 기능을 확장하면서 Codex 실행 엔진을 유지할 수 있다. |
| Codex 전체 소스를 포크해 관리 기능 추가 | 배너와 내부 메뉴까지 바꿀 수 있으나 upstream 변경 추적 범위가 커진다. 기본 설계에는 필요하지 않다. |

관리 TUI는 Go의 [Bubble Tea](https://github.com/charmbracelet/bubbletea)를 사용한다.
목록에서 Enter 또는 `/open`을 사용하면 새 터미널에서 해당 작업의 app-server에
공식 Codex TUI를 연결한다. 관리 화면과 채팅 화면을 동시에 사용할 수 있다.
인증은 선택한 계정의 환경으로 격리하고 전역 기본 계정은 바꾸지 않는다.
계정 전환으로 실행이 교체되면 같은 터미널이 새 실행에 다시 연결된다.
Mac에서는 Terminal 새 창을 열고, GUI가 없는 SSH 환경에서는 별도 이름의 tmux 화면과
attach 명령을 제공한다. CLI `codexm attach JOB_ID`는 현재 터미널에서 연결한다.
서로 다른 app-server와 계정에 속한 작업을 모아야 하므로 통합 목록은 `codexm`이 소유한다.
기존 `codex agents`의 목록 화면을 그대로 전체 관리자 화면으로 취급하지 않는다.

app-server와 remote TUI는 실험적 인터페이스다. 설치된 Codex에서 생성한 스키마를
기준으로 호환성을 확인하며, 최소 연동 검증을 통과한 버전을 사용한다.
실행 중인 작업의 Codex 바이너리는 자동으로 교체하지 않는다.
[공식 app-server 문서](https://learn.chatgpt.com/docs/app-server)

## 작업과 채팅의 관계

관리하는 단위와 실제 Codex 대화를 구분해야 계정 전환이나 후속 작업에도
사용자가 보고 있는 작업이 유지된다.

| 단위 | 역할 |
| --- | --- |
| Workspace | 실행 호스트, 실제 작업 경로, 선택적인 Git worktree와 접근 정책 |
| Job | 사용자가 관리하는 작업. 제목, 종류, 요청, 완료 조건, 계정 정책과 부모 작업을 가진다. |
| Thread | 실제 Codex 채팅. 호스트와 대화 저장소 및 thread ID로 식별한다. |
| Run | 한 계정과 실행 환경에서 진행한 실행 회차. 교체할 때마다 새 회차를 기록한다. |
| Goal | 해당 Thread에 존재할 수 있는 선택적 지속 목표 |

보통 하나의 Job에 하나의 Thread를 연결한다. 사용자가 별도 분기를 요청하면
새 Thread를 연결한 자식 Job을 만든다. 후속 지시는 같은 Job과 Thread에 추가한다.
관리자 자체의 판단 세션은 작업 목록과 복구 대상에서 분리한다.

동일한 thread ID라도 호스트나 대화 저장소가 다르면 같은 실행으로 간주하지 않는다.
관리자 UI의 작업 계층과 Codex 내부에서 생성한 native subagent 계층도 구분한다.
native subagent는 부모 실행 관계를 추적해 함께 표시하며, 부모의 동작과 충돌하도록
개별 자식을 임의로 다른 계정에서 다시 시작하지 않는다.

| 작업 종류 | 한 턴이 끝났을 때 | 완료 기준 |
| --- | --- | --- |
| 일반 채팅 | `idle`로 남아 추가 지시를 기다린다. | 사용자가 닫거나 보관한다. |
| 단발 작업 | `result_ready`로 전환한다. | 사전에 정한 검사 통과 또는 사용자의 완료 판단 |
| 지속 목표 | 현재 목표 상태를 조회한다. | Codex의 목표가 `complete`가 됨 |
| 여러 하위 작업을 가진 작업 | 각 자식 결과와 의존성을 갱신한다. | 등록된 하위 작업 및 부모의 완료 조건 충족 |

`turn/completed`와 프로세스 종료 코드만으로 Job 전체를 완료 처리하지 않는다.
반대로 목표가 없는 일반 채팅에 자동으로 `/goal`을 만들거나 매 턴 `계속해`를
보내지 않는다. 단발 작업의 완료 조건이 없으면 결과 준비 상태에서 멈춘다.

## 최초 설정과 계정 저장

최초 `codexm` 실행은 다음 순서로 동작한다.

1. 기존 `~/.codex-accounts`에서 닉네임을 읽는다. 새 작업 계정은 관리 화면의 로그인으로 등록한다. `codexm account NAME`은 native 터미널 선택이다.
2. 관리 에이전트용 계정을 반드시 선택하게 한다. 현재 요청에서는 `account-backup`을
   추천 표시할 수 있지만 사용자 선택 없이 확정하지 않는다.
3. 선택한 계정의 인증을 확인하고, 사용할 모델과 설정을 확인한다.
4. 로컬 설정 파일에 계정 닉네임을 원자적으로 저장한다. 인증 토큰은 기존 계정
   저장소가 계속 소유한다.
5. 다음 실행에서는 저장된 선택을 불러온다. 설정을 바꿀 때만 선택 화면을 다시 연다.

설정 파일은 `~/.config/codexm/config.toml`이다. 계정이 삭제되거나 인증이 만료되면
그 상태를 표시하고 다시 선택하거나 로그인할 수 있게 한다. 네트워크 실패 때문에
저장된 선택을 지우거나 다른 관리자 계정으로 바꾸지 않는다.
새 장비에서는 계정 등록과 최초 선택을 다시 수행한다.

관리 계정은 자연어 관리 지시와 예외 판단에 사용한다. 작업 계정의 우선순위와
한도 전환 정책은 별도 설정이다. 같은 닉네임을 양쪽에 사용하더라도 역할별 호출과
토큰 사용량을 나누어 기록한다. 관리자 계정이 소진돼도 감시와 규칙 기반 복구는
계속 실행하고, 모델 판단이 필요한 사건만 대기시킨다.

## 터미널 화면과 조작

기본 화면은 작업 목록, 선택한 작업의 상태 요약, 관리 명령/검색 입력창으로 구성한다.
상단에는 관리자 계정, 감시 연결 상태와 작업 수를 표시한다. 계정별 한도는
확인 시각과 함께 보여 주며 조회 실패를 잔여량 0으로 표시하지 않는다.

입력창에 기본 포커스를 둔다. 일반 텍스트를 입력하고 Enter를 누르면 작업을 검색한다.
`/manager`로 관리 모델 입력을 명시적으로 선택했을 때만 자연어 관리 판단을 요청한다.
`/filter`로 검색 입력에 돌아온다. 채팅과 추가 지시는 `/open`으로 연 공식 Codex에서 입력한다.
Tab으로 목록, Shift+Tab으로 미리보기 영역을 선택한다. 목록에서 ↑↓로 작업을 선택하고
Enter를 누르면 새 터미널로 연다. PgUp/PgDn은 입력창 포커스와 초안을 유지하면서
정보 영역을 스크롤한다.

`/`를 입력하면 관리 명령 목록이 열리고 이름을 입력할수록 목록이 좁혀진다.
↑↓ 선택, Tab 완성, Enter 실행, Esc 닫기를 지원한다. 도움말은 같은 명령 목록에서 생성한다.
관리 명령에는 별도 접두사를 붙이지 않는다. `/model`, `/permissions`, `/goal` 등
Codex 채팅 기능은 새 터미널의 공식 Codex가 제공한다.

| 명령 또는 화면 | 동작 |
| --- | --- |
| `codexm`, `/agents` | 최초 관리자 계정 저장 후 관리 목록·검색·상태 필터·계층 표시 |
| `/open` 또는 목록 Enter | 선택한 계정/세션의 공식 Codex를 새 터미널에서 열기 |
| `/new` | 작업 폴더·계정·제목을 지정하고 빈 새 채팅을 공식 화면에서 열기 |
| `/chats [검색어]` | 저장된 대화를 검색하고 계정을 선택해 새 터미널에서 열기 |
| `/status`, `/usage` | 전체 감시 상태 또는 전체 계정 한도·관리자 호출·세션별 토큰 |
| `/info` | 선택한 세션의 모델·권한·목표 상태·토큰·계정 요약 |
| `/accounts` | 모델 호출 없이 전체 계정 한도를 새로 조회 |
| `/manager-account [NAME]` | 저장된 관리자 계정 조회·변경 |
| `/pause`, `/resume`, `/stop` | 선택 작업 일시 중지·실행 재개·종료 |
| `/logs`, `/logs all`, 목록에서 `l` | 선택 작업 또는 전체 실행 로그를 자동 갱신 |
| `/read`, `/older`, `/events`, `/settings` | 대화 미리보기·이전 페이지·사건·설정 요약 |
| `/manage`, `codexm manage JOB_ID` | 기존 대화를 생성 없이 관리 대상으로 보관 |
| `/manager [지시]` | 필요할 때 짧은 관리자 모델 호출 |
| `/filter [검색어]`, `/state [상태]` | 목록 검색/상태 필터. 빈 인수로 해제 |
| `/quit` | 관리 화면만 닫고 실행/감시 유지 |
| `/shutdown` | 관리한 실행과 감시 서비스를 종료 |

새 빈 채팅은 제목을 저장해 공식 화면에서 즉시 불러올 수 있게 준비한다.
대화 열기는 실행 환경만 준비하며 중단된 입력을 다시 보내거나 완료 목표를 재개하지 않는다.
완료/일시 중지 상태와 목표 예산·누적 사용량을 유지한다. 실제 실행 재개는 `/resume`,
추가 지시는 공식 화면에서 명시적으로 수행한다. 공식 화면의 `/quit`는 화면 연결만 닫는다.
완료된 목표의 실행은 연결된 화면이 있는 동안 유지하고 마지막 화면이 닫히면 정리한다.
끊어진 화면 연결은 heartbeat 만료로 감지하므로 강제 창 닫기도 처리한다.

다른 Codex 프로세스가 소유한 대화는 먼저 그 프로세스를 종료해야 인계할 수 있다.
관리 프로그램은 해당 프로세스를 임의로 종료하지 않는다. 비대화형 접근에는
`status --json` 등 동일한 관리 API의 CLI를 제공한다.

## 간단한 작업로그

`codexm logs`는 세션 ID와 작업 ID, 실행 계정, 시작·종료 시각, 실행시간,
기본·보조 한도 사용률의 시작→최신 관측값, 마지막 확인 시각을 표시한다.
계정 선택과 변경은 시각·이전 계정·새 계정·사유를 따로 기록한다.
TUI의 `/logs`는 선택한 작업, `/logs all` 또는 목록의 `l`은 전체 기록을
보여준다. 화면에 현재 조회 범위를 표시한다.
로그 화면은 2초마다 갱신하며, 계정 한도는 기본 60초마다 기존 app-server에서 조회한다.
이 과정에는 관리자나 하위 작업 모델 호출이 없다.

실행시간은 해당 계정의 작업 실행 환경을 열어둔 시간으로 대기도 포함한다.
한도 %는 그 계정 전체의 값이다. 다른 Codex 세션이 같은 계정을 쓰면 그 사용도 포함되므로
특정 세션이 사용한 %로 간주하지 않는다. 같은 갱신 구간일 때 관측 차이를 `%p`로 표시하고,
한도가 갱신되거나 종류가 바뀌면 차이를 계산하지 않는다. 조회 실패나 미측정 값은 `?`다.
인계 이전의 계정·시간·사용량은 기록으로 확인할 수 없는 경우 추측하지 않는다.

실행 구간과 표본은 로컬 `state.sqlite`에 저장하고, 종료·재시작 뒤에도 시작 시각을 유지한다.
supervisor가 종료된 뒤의 `codexm logs`는 저장된 DB를 읽으며 감시 서비스를 시작하지 않는다.
한도 조회 간격은 로컬 설정의 `[logging] usage_sample_seconds = 60`으로 조절한다.
실제 인계와 화면 검증은 [0.1.1 로컬 인계 검증](codexm-handoff-validation.md)에 기록했다.
명령 목록·입력 기본 포커스·사용량 요약 검증은 [0.1.2 TUI 검증](codexm-tui-validation.md)에 있다.

`codexm usage`도 전체 사용량을 요약해서 출력하며 원본 데이터가 필요할 때만
`codexm usage --json`을 사용한다. TUI 상태·사용량 화면에는 목표 본문, 대화 내용,
관리자 판단 프롬프트 같은 내부 JSON을 펼치지 않는다. 한도 조회 실패와 미측정 토큰은
0으로 표시하지 않는다. 확인 시각과 한도 갱신 시각은 로컬 시간으로 표시한다.

## 상주 프로그램과 실행 환경

Go 프로그램 내부를 TUI, 상태 관리, Codex 연결, 계정 정책, 저장소와 관리자 호출로 나눈다.
TUI를 닫아도 상태 관리가 살아 있도록 supervisor는 이름 있는 tmux 세션에서 실행한다.
작업별 Codex 실행 환경도 별도 tmux 세션과 로컬 Unix 소켓을 사용한다.

```text
codexm TUI
  └─ 로컬 관리 연결
      └─ codexm supervisor
          ├─ 사건 저장 및 미처리 동작 큐
          ├─ 작업 상태와 계정 정책
          ├─ 작업별 Codex app-server 연결
          └─ 필요할 때만 관리 에이전트 호출
```

기본 세션 이름은 `codexm-supervisor`와 `codexm-job-<짧은 작업 ID>-<실행 ID>`다.
실제 생성한 이름과 정확한 `tmux attach -t <이름>` 명령을 화면과 상태 조회에 제공한다.
완료한 작업의 실행 환경은 정리하되 Job과 Thread 기록은 보존한다. 일반 채팅이
유휴 상태이면 실행 환경을 내려도 다음 지시 때 같은 Thread를 다시 열 수 있다.
접속한 UI, 진행 중인 작업과 복구 대기가 모두 없으면 supervisor 세션도 정리한다.

동시에 여러 TUI가 접속해도 실행을 결정하는 supervisor는 장비당 하나다.
각 Thread에는 하나의 실행 소유자만 둔다. 계정 전환은 대상 작업의 자식 환경에만
적용하고 전역 로그인, 다른 터미널의 환경, 다른 작업의 실행 설정은 바꾸지 않는다.
Codex 대화 저장소는 기존 저장소를 사용하고, `codexm` 상태 DB는 별도 경로에 둔다.
환경 변수와 명시적인 `sqlite_home` 설정의 우선순위까지 함께 검증한다.

같은 작업 폴더에 쓰는 두 작업은 충돌 가능성을 표시하고 기본적으로 순서를 조정한다.
병렬 편집은 별도 worktree 또는 사용자가 지정한 분리된 경로를 사용한다.
읽기 전용 작업은 별도로 분류할 수 있다. Git 작업의 검증·commit·push는 해당 작업의
완료 조건과 기존 지시를 따르며, 관리자가 다른 작업의 변경을 한꺼번에 커밋하지 않는다.

## 사건 저장과 누락 복구

관리 상태는 사건마다 모델이 다시 추론하지 않고 저장된 상태에서 계산한다.
최소 저장 단위는 `jobs`, `thread_refs`, `runs`, `events`, `actions`,
`account_snapshots`, `manager_decisions`다.

1. 공식 상태·턴·오류·목표 변경과 입력·승인 요청을 수신한다. 프로세스 종료와
   소켓 끊김은 별도의 관측 사건으로 만든다.
2. 사건, 최신 상태와 필요한 동작을 같은 SQLite 트랜잭션으로 기록한다.
3. 실행기가 저장된 동작을 처리하고, 관측한 결과를 다시 기록한다.
4. 기본 30초 간격으로 실제 실행·Thread·Goal 상태를 대조한다.
5. 재접속·재시작 시 이전 실행 회차와 미처리 동작을 확인하고 이력 조회로 보완한다.

텍스트 조각은 실시간 렌더링용으로 묶을 수 있지만 오류·상태 변경·턴 종료·승인·
사용자 입력 요청은 일반 출력량 때문에 버리지 않는다. 기록을 따라잡지 못하면
감시 지연을 표시하고 새 자동 동작을 제한한다. 저장 실패를 정상 감시로 표시하지 않는다.

서버 이벤트에 재전송 보장이 있다고 가정하지 않는다. 수신한 사건은 저장하고,
수신하지 못한 구간은 현재 상태와 영속 이력으로 복구한다. 대조할 수 없는 구간은
`unknown`으로 표시한다. 기존 미해결 질문을 재확인할 수 없으면 임의 답변 없이
관리 화면에서 사용자가 해당 채팅을 열도록 연결한다.

동작에는 고유 ID와 실행 회차를 기록해 같은 사건으로 두 번 시작하지 않게 한다.
서버가 턴 시작을 받아들인 직후 연결이 끊긴 경우에는 현재 턴과 메시지 이력을
먼저 대조한다. `clientUserMessageId` 같은 상관관계 필드가 있다는 이유만으로
서버의 중복 제거를 보장한다고 가정하지 않는다. 결과가 불명확한 명령은 그대로
재전송하지 않고 `outcome_unknown`으로 남긴다.

정상적인 장시간 도구 실행과 사용자 중단, 입력 대기, 계정 제한, 연결 장애를
서로 구분한다. 단순히 새 출력이 없다는 이유만으로 프로세스를 재시작하지 않는다.

## 계정 전환과 관리자 호출

작업 계정 우선순위는 설정 값이며 코드에 계정명을 고정하지 않는다.
현재 사용할 예시 정책은 `account-work → account-secondary → account-main → account-backup`이다.
최초 작업에 지정한 계정을 적용하고, 사용 한도 소진 시 우선순위대로 재선택한다.

작업용 `account-backup`은 앞의 세 계정이 모두 한도 소진으로 확인됐을 때만 사용한다.
이 계정으로 작업하는 동안 앞의 세 계정을 600초마다 조회하고, 사용 가능한 계정이
확인되면 즉시 전환 절차를 시작한다. 계정 조회 실패나 인증 오류는 한도 소진과 다르다.
일반 사용 가능 여부와 해당 모델의 한도 버킷을 확인하고, 잔여 퍼센트·초기화 시각만으로
회복을 단정하지 않는다. 계정별 조회와 인증 갱신은 동시에 중복 실행하지 않도록 조정한다.

전환은 다음 단계로 저장한다.

```text
전환 요청 저장 → 턴 중단 및 기존 소유권 해제 확인
→ 새 계정 환경 생성 → 같은 Thread 재개 → 작업 종류에 맞게 진행 확인
```

공식 TUI를 쓰는 실행에서는 `/exit`를 통한 종료를 지원하고, app-server를 직접
관리하는 실행에서는 정상 턴 중단과 해당 실행 종료로 같은 인계 절차를 구현한다.
TUI 창이 닫혔다는 사실만으로 app-server와 실행 중인 턴이 종료됐다고 판단하지 않는다.
실행 중인 외부 작업은 결과를 확인한 뒤 인계하며, 다른 작업의 프로세스를 정리하지 않는다.
계정 변경만으로 모델·reasoning·cwd·권한·목표 예산을 변경하지 않는다.

이전 `Run`에서 발생한 늦은 오류는 새 실행을 중단시키지 못하게 한다.
전체 계정 소진은 대기 상태로 두고, 순간 요청 제한과 서비스 장애는 제한된 재시도로 처리한다.
컨텍스트 부족이나 목표 예산 소진을 계정 전환으로 해결하려고 반복하지 않는다.

관리 에이전트 호출 사유는 자연어 관리 지시, 반복 실패의 해석, 결과 충돌,
다음 하위 작업을 정해야 하는 경우 등으로 제한한다. 일반 턴 완료, 계정 한도 조회,
명확한 한도 전환과 화면 탐색마다 관리 에이전트를 호출하지 않는다.

입력은 작업 계약, 관련 사건, 최근 필요한 대화와 이전 판단 요약으로 구성한다.
관리자 대화 전체를 계속 누적해 전달하지 않는다. 최초 구현은 일회성 판단 세션을
사용하고, 장기 기억은 로컬의 짧은 결정 기록으로 유지한다.
`create_job`, `send_input`, `retry`, `wait`, `needs_user` 등 제한된 결과를 검증한 뒤
프로그램이 실행한다. 관리자 모델이 임의 셸 명령을 반환해 그대로 실행하는 방식은 쓰지 않는다.

관리자가 새 작업을 생성하는 기능은 사용자의 위임 범위, 작업 폴더, 완료 조건,
동시 실행 수와 하위 작업 깊이를 함께 확인한다. 지원되지 않는 동작은 실행하지 않고 표시한다.
허용된 지시 범위의 일반 판단은 이어서 진행하고, 사용자만 답할 수 있는 정보나
기존 권한 정책이 요구하는 승인은 대기 상태로 전달한다.
관리자 호출 실패는 사건을 삭제하지 않으며 같은 사건의 무한 재호출을 막는다.

## home 저장소와 로컬 상태

제품 소스와 빌드·설치 절차는 독립 `codeasy-digix/codexm` 저장소가 원본이다.
`~/.home`은 고정한 소스 revision의 복구와 설치 호출, 환경 설명과 설정 예시를
관리한다. `manifests/home.json`이 의존성·설정·상태·doctor 검사를 등록하며,
`~/.local/bin/codexm` 실행 링크는 독립 설치기가 소유한다.

| 경로 | 용도 | Git 추적 |
| --- | --- | --- |
| `codeasy-digix/codexm` | Go 소스, 상태 스키마, 빌드·설치·배포 준비 | 예 |
| `~/.home/tools/codexm/` | 독립 소스 복구·빌드·설치 호출 | 예 |
| `~/.home/docs/codexm.md` | 동작과 개발 설계 | 예 |
| `~/.home/docs/infos/info-codexm.md` | 환경 복구와 설치 계약 | 예 |
| `~/.home/templates/codexm/config.example.toml` | 계정 정책과 최초 설정 예시 | 예 |
| `~/.local/share/codexm/versions/<version>/<platform>/codexm` | 설치된 실행 파일 | 아니오 |
| `~/.local/share/codexm/engines/<hash>/` | 보관한 공식 Codex와 보조 엔진, SHA-256 영수증 | 아니오 |
| `~/.local/bin/codexm` | 선택한 설치 버전을 가리키는 진입점 | 아니오 |
| `~/.config/codexm/config.toml` | 장비별 관리자 선택과 실제 사용자 설정 | 아니오 |
| `~/.local/state/codexm/` | 상태 DB, 사건, 판단 기록과 소켓 | 아니오 |
| `~/.codex-accounts/<name>/` | 기존 계정의 인증 저장소 | 아니오 |
| `~/.codex/` | 기존 Codex 대화 저장소 | 아니오 |

소스 구조는 다음과 같다.

```text
codexm/
  cmd/codexm/       명령 진입점
  internal/tui/    작업 목록과 입력 화면
  internal/manager/ 관리자 요청과 결과 검증
  internal/jobs/   작업 종류와 상태 전이
  internal/runtime/ Codex 연결과 실행 환경
  internal/accounts/ 계정 조회와 전환
  internal/store/  사건 저장과 복구 큐
  internal/activity/ 간단한 실행·계정 사용률 표시
  internal/policy/ 자동 실행과 완료 규칙
  internal/cli/    비대화형 관리 명령
  build.sh        플랫폼별 정적 실행 파일 빌드
```

`~/.config/codexm` 전체를 `.managed-paths`로 연결하지 않는다. 최초 선택과 장비별
실행 설정이 의도치 않게 저장소 파일을 수정하지 않도록 설정 예시에서 별도로 생성한다.
사용자가 공통 정책을 백업하려면 인증과 실행 상태를 제외한 명시적인 내보내기를 제공한다.
독립 소스는 `./install.sh --build`로 설치한다. `.home`은
`config/home/codexm-revision.txt`의 Git commit을 고정해 그 설치기를 호출한다.
현재는 배포 준비만 하므로 새 Release/tap/npm 게시가 없다. `.home`은 설치된
codexm을 보존하며 실행 파일의 선택·업데이트는 독립 설치기가 소유한다.
진행 중인 supervisor·작업은 실행 경로와 엔진을 유지한다.

## Codex 업데이트와 버전 보관

업스트림 Codex 자동 업데이트와 codexm 실행을 분리한다. 최초 연결에서는 공식
실행 파일의 버전·SHA-256·필수 app-server 스키마를 확인한 뒤 `codex`와
`codex-code-mode-host`를 전용 경로에 보관한다. 작업마다 이 경로와 버전을 저장하고,
계정 교체·관리자 재시작·공식 TUI 접속에도 같은 엔진을 쓴다. 공식 화면에서는
시작 시 업데이트 확인을 끈다. Codex 업데이트를 생략해도 보관한 엔진으로 실행한다.

```sh
codexm doctor --json
codexm runtime refresh    # 명시적으로 새 호환 엔진 검증 및 선택
```

`runtime refresh`가 실패하면 이전 선택을 유지한다. 성공한 새 선택은 다음 supervisor
시작에서 새 작업에 적용하며 기존 Job의 엔진 기록은 보존한다. 새 Codex 버전이
공용 대화 DB나 로그 형식을 비호환으로 바꾸는 경우까지 실행 파일 보관만으로
보장하지 않는다. 검증 기준 버전은 0.162.1이며 새 계열은 스키마 확인과 실제 재개
검사를 거쳐 채택한다. 대화·목표·인증 저장소는 공식 저장소에 그대로 남는다.

긴 대화는 최근 20턴부터 페이지로 읽고 `/older`로 앞선 기록을 불러온다.
출력 조각은 메모리 미리보기로 처리하며 완료 항목·상태·승인·전환은 SQLite에 저장한다.
Unix 소켓 경로가 길어지면 현재 사용자가 소유한 0700 `/tmp/codexm-<uid>-<hash>/`를 쓴다.
재시작 중에 전송 결과를 확인하지 못한 입력은 다시 보내지 않는다. 기록 확인 후
`codexm resolve-action ACTION_ID done|cancelled`로 명시적으로 정리한다.
작업 계정 정책은 로컬 TOML에서 바꾸고 다음 supervisor 시작에 적용한다.

Codex 명령을 셸 문자열로 조립하기보다 실행 파일과 인자 배열로 호출한다.
기존 계정 컨트롤러를 통한 자식 환경 구성을 재사용하고, 사람용 상태 출력은 파싱하지 않는다.
설정 저장은 기존 파일을 보존하면서 원자적으로 교체하고 스키마 버전을 관리한다.
현재 DB 스키마는 1이며 다른 스키마는 변경 없이 거부한다. 향후 마이그레이션은
별도 백업과 복구 경로를 갖춘 뒤 추가한다. 대화 본문을 관리자 DB에 무제한
복제하지 않고 필요한 사건·참조·판단 요약만 저장한다.

## 구현 순서와 검증 기준

1. **공식 런타임 연동 검증:** 임시 대화로 새 Thread 생성, 기존 Thread 재개,
   추가 지시, 상태 구독, 공식 TUI 연결·종료와 계속 감시를 확인한다.
   계정 교체 시 같은 대화와 목표가 보존되고 실행 소유자가 하나인지 확인한다.
2. **관리 TUI와 작업 모델:** 최초 계정 선택·저장·재사용, 목록·검색·새 채팅·
   기존 대화·입력 큐를 구현한다. 일반 대화가 자동으로 무한 진행되지 않아야 한다.
3. **영속 상태와 복구:** 사건 저장, 미처리 동작, 재시작 대조와 입력 대기를 구현한다.
   연결 단절, 사건 중복·순서 변경, 저장 오류와 전환 도중 종료를 재현한다.
4. **계정 정책:** 소진 전환, 전체 소진 대기, 600초 확인, 상위 계정 복귀를 검증한다.
   인증·통신 오류를 소진으로 오판하지 않고 목표 예산도 바꾸지 않아야 한다.
5. **관리 에이전트:** 짧은 자연어 관리 지시, 예외 판단, 허용된 새 하위 작업 생성과
   결과 검증을 연결한다. 관리자 한도 소진·잘못된 응답에도 감시가 유지돼야 한다.
6. **설치와 실제 인계:** macOS와 Linux에서 TUI·tmux·경로·설정을 확인하고,
   검증된 작업부터 실제 관리 대상으로 가져온다. 각 작업 종료 후 해당 세션을 정리한다.

각 구현 단위는 필요한 검사와 commit·push를 마친 뒤 다음 단계로 진행한다.
아래 시나리오는 전체 동작 검증에 포함한다.

- `/goal` 없이 새 질문을 보내고 응답 후 대기하며 같은 채팅에 후속 질문을 보낸다.
- 기존 대화를 검색해서 내용을 보고 추가 지시를 보낸다. 단순 열람에는 실행을 만들지 않는다.
- 기존 목표가 있는 작업을 가져와 목표와 사용량을 유지한다.
- 실행 중인 다른 터미널의 대화를 발견했을 때 중복 writer를 만들지 않는다.
- 작업 화면에서 관리자에게 잘못 입력하거나 그 반대 상황이 생기지 않도록 대상을 표시한다.
- 입력·승인 대기와 실제 실패를 구분하고, 사용자가 멈춘 작업을 자동 재개하지 않는다.
- 응답 유실 뒤 같은 사용자 지시가 두 번 전송되지 않는지 확인한다.
- 이전 실행의 늦은 사건으로 계정 전환이나 관리자 판단이 중복 실행되지 않는다.
- TUI 연결을 닫거나 재접속해도 진행 중인 작업과 관리자 상태를 복구한다.
- 같은 작업 폴더의 동시 편집을 조정하고, 완료 시 해당 작업의 실행 환경만 정리한다.
- 정상 작업·목록 조회·사용량 확인·정해진 계정 전환의 관리자 모델 호출 수는 0이다.

설계 근거는 [공식 app-server API](https://learn.chatgpt.com/docs/app-server),
[공식 CLI 명령](https://developers.openai.com/codex/cli/reference),
[계정 관리·현재 실행 계약](../README.md)이다.
